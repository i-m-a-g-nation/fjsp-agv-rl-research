# 用户目标：受约束的自动科研迭代

2026-10-25，用户进一步明确：需要工作流自己获取论文及相应源码，提取并验证有价值的设计，复现或适配，执行训练/对比，依据结果反复改进，逐步接近大创与毕设目标；不应要求用户另找AI手动分派每个任务。

本文记录需求及已核实缺口，**不是已实现能力、实施方案批准或新实验预算**。原始课题、模型假设、合法性检查和已有证据继续保留。先前用户选择优先毕设，且希望尽量在2027年3月前完成；大创生产—物流要求不能被生产—维护问题替代。

## 一次启动应承担的工作

1. 从课题缺口提出本轮可检验的问题，而非仅按论文标题生成建议。
2. 获取相关论文与公开实现，确认论文/版本/代码仓库关联，保存可追溯原文与代码位置。
3. 提取模型假设、状态、动作、奖励、网络、训练方法和评价设置，区分原文、源码行为及AI建议。
4. 区分“原方法复现”“局部设计复用”“针对本项目改造”，说明哪些假设/指标不适用；引用了论文不等于完成复现。
5. 自动形成隔离的候选代码变更，运行基线、环境、目标和可行性检查，失败自行定位/修复或停止。
6. 在明确预算内训练和比较，保存真实配置、模型、日志、数据身份、计划与失败记录。
7. 根据验证结果决定保留、回退、修复、调参或更换假设；不能只在代码报错时重试，也不能将每次运行强行写成改进。
8. 在预算、停滞或范围边界处停止，交付本轮项目变更和证据，让后续批次从已有状态继续。

多个AI角色和所需工具由工作流内部组织；用户只面对统一启动、进度、需决策事项和结果入口。聊天中的编码代理替项目做事，不能计作该程序自身已经拥有的能力。

## 每轮应交付的结果

- 本轮问题及其与课题要求的关系。
- 论文/源码依据，以及复现或适配的差异说明。
- 可审查、有版本的候选代码与训练产物，不只有文本报告。
- 同条件基线与候选结果、有效性检查、失败及适用限制。
- 保留/回退/继续/停止的理由，下一轮候选问题和可复跑入口。

代码变更、训练模型和科研结论分别记录；运行结束不自动代表课题达标。

## 防止偏离的要求

- 大创与毕设分别绑定原始要求，建模范围改变需要显式处理，不靠RAG文本或模型自述覆盖。
- 基线、领域checker和评价目标保持独立；候选不得通过降低检查、改变目标或省略维护/运输来赢得比较。
- 训练/验证/最终测试隔离；按验证结果选择设计与超参数，最终测试不作为反复调参反馈。
- 输入、源码、配置、模型和证据具有版本身份；保留失败分母与资源消耗，禁止挑选最佳种子冒充整体效果。
- 批次范围和预算事先明确；批次内自动执行。改变研究问题、关键假设或资源额度时，再交由人判断。
- 独立审查与确定性检查共同约束；不声称多AI讨论能够保证科研正确，也不保证每轮提升或论文录用。

RAG在上述流程中提供材料检索与上下文，不承担代码执行、训练、实验决策或课题验收。后续改造应以一条真实可运行的科研闭环为验收，不能以文档、角色、索引或护栏数量替代。

再后“继续”完成[两条状态事实及单独模型语义复核](paper_state_semantic_validation.md)：新批次4次、14.188主动秒，引用2/2定位、两个模型supported判断均未获人审。已有具体维护兼容编码方案，但未实现、训练或证实收益；原有R1已经具备全部任务/机器信息。
