# FJSP Research Platform Roadmap

最后审阅：2026-07-14  
当前活动阶段：Phase 2A  
路线类型：长期研究平台，按阶段评审推进

## 1. 文档目的

本文件定义项目的长期方向、阶段边界、阶段交付物和进入/退出条件。

本项目采用以下文档分工：

- `docs/ROADMAP.md`：管理长期目标和阶段推进规则。
- `AGENTS.md`：管理当前阶段允许实施和明确禁止的内容。
- `README.md` 与 `README.zh-CN.md`：说明当前已经实现和实际验证的状态。
- `docs/review_status.md`：记录最近一次技术审查与验证证据。
- `notes/`：保存文献、候选方案和尚未批准的研究讨论。

当这些文件发生冲突时，开发范围以仓库内当前版本的 `AGENTS.md` 为准；
长期方向以本文件为准；实际完成状态必须以测试、实验产物和版本记录为准。

## 2. 长期使命

建设一个正确、可验证、可复现、可逐层扩展的柔性作业车间调度研究平台，
支持从静态 FJSP 逐步研究动态扰动、运输资源、AGV 协同调度和学习型决策方法。

长期平台的最终能力目标是：

1. 使用统一数据模型表达静态和动态柔性作业车间问题。
2. 使用统一调度结果接口连接启发式、精确方法、元启发式和学习方法。
3. 使用独立的 feasibility checker 拒绝非法调度。
4. 对机器、工序、动态事件和运输资源进行可审计的状态转换。
5. 使用标准 benchmark、固定实验协议和结构化产物比较不同算法。
6. 为论文研究提供可复现的模型、基线、消融实验和结果证据。

长期使命不表示 AGV、RL、GNN 或多智能体已经被批准为当前开发任务。
任何下一阶段都必须在上一阶段退出评审通过后单独启用。

## 3. 核心原则

项目在所有阶段遵循以下顺序：

```text
正确性 > 可维护性 > 可复现性 > 性能 > 功能数量
```

具体要求：

- 任何求解或重调度结果在返回和记录前必须通过对应层级的 feasibility checker。
- 不得为了测试通过而放宽约束或隐藏失败结果。
- 数据模型、调度语义、动态事件语义和实验协议由项目统一管理。
- 通用计算能力优先使用成熟库，例如 OR-Tools、Matplotlib 和 pytest。
- 新阶段必须复用已验证接口，不得绕过现有合法性检查重新建立平行体系。
- benchmark、随机种子、运行预算、依赖版本和失败记录必须可追溯。
- 增加 AGV、动态事件、RL、GNN 或多目标并不自动构成学术创新。
- 研究贡献必须由文献差距、强基线复现、对照实验、消融实验和结果分析支持。

## 4. 混合架构与自研边界

本项目不再以“自行实现一个覆盖所有能力的通用调度库”为目标。长期采用混合架构：

```text
外部实例或场景
    -> 项目统一问题语义
    -> 自研或公开库求解后端
    -> 项目统一 ScheduleResult
    -> 项目独立 feasibility checker
    -> 项目实验协议、结果和报告
```

### 项目自有核心

以下内容直接决定研究问题的语义、正确性和可复现性，由本项目维护：

- 静态、动态和未来运输问题的统一数据契约。
- `ScheduleResult` 以及未来加工、运输记录的统一输出契约。
- 静态、动态和未来 AGV 分层 feasibility checker。
- 动态事件时间线、冻结记录、剩余工序和重调度语义。
- Benchmark 来源、随机种子、运行预算、失败语义和结构化实验产物。
- 论文特有的状态、动作、目标、约束和评价指标。

### 优先复用的外部能力

通用能力在自行实现前必须评估成熟库：

| 外部能力 | 预期角色 | 当前决定 |
|---|---|---|
| OR-Tools | CP-SAT、精确/限时参考模型、未来运输资源约束 | 正式后端，继续使用 |
| JobShopLib | Dispatcher、公开基线、可视化、未来 RL/GNN 环境候选 | 先验证兼容性，不设为核心依赖 |
| PyJobShop | 丰富 CP 约束和复杂静态调度参考 | 作为候选基线，按需求引入 |
| Matplotlib / pytest | 绘图和自动测试 | 继续使用 |

公开库的输出只有转换成项目统一结果并通过项目 checker 后，才能进入实验记录。
项目不得仅因为已经投入过自研成本而拒绝更合适的公开实现，也不得在兼容性未经验证时全面迁移。

### 公开库兼容性试验

在新增通用调度基础设施前，先用以下最小试验判断是否复用：

1. 选择 toy 3x3、一个 Fattahi 小实例和一个 Brandimarte 中等实例。
2. 将当前 `FJSPInstance` 转换为候选库实例。
3. 使用候选库的公开算法或求解器生成调度。
4. 将输出转换回当前 `ScheduleResult`。
5. 使用当前 feasibility checker 重新验证。
6. 比较模型语义、makespan、运行时间、错误行为和维护成本。

试验通过后才决定采用适配器、仅作为外部基线或不引入该库，禁止先进行全面迁移再验证。

## 7. Phase 1：静态 FJSP 基础实验平台

**状态：`Complete`**

**维护模式：Frozen（冻结扩展，仅允许加固和兼容性维护）**

### 作用

建立所有后续研究共同依赖的问题模型、调度接口、合法性裁判和实验基准。

### 已有交付物

- FJSP 实例、Job、Operation 和 MachineOption 数据模型。
- 标准 FJSPLib 风格实例加载与机器编号归一化。
- `ScheduleRecord` 和 `ScheduleResult` 统一调度结果。
- 半主动解码和静态 feasibility checker。
- FIFO、SPT、EFT、MWKR、MOPNR 和随机基线。
- OR-Tools CP-SAT 小规模参考求解器。
- Gantt 图、CSV、质量报告、LB/UB 元数据和自动测试。

### 后续维护要求

- 修复审查发现的不可变性、底层接口可绕过校验和 Gantt 自动测试缺口。
- 保持静态 checker 独立、严格和向后兼容。
- 提取静态与动态共享的最早开始时间和资源日历核心，但不提前加入 AGV 抽象。
- 通过适配器评估公开库；不因适配而改变项目统一结果和 checker 契约。
- 只有研究问题需要时才扩展 benchmark，并同步更新来源、许可证、LB/UB 和审计结果。

### 停止投入项

Phase 1 不再主动投入以下扩展：

- 新增更多普通 dispatching rule。
- 新增 CP-SAT worker、时间限制和重复运行扫描。
- 新增只重复现有信息的静态报告脚本。
- 自行扩展通用 Gantt、GIF、视频和可视化框架。
- 自行建设通用 RL、GNN 或仿真基础设施。
- 为了与成熟公开库比功能数量而增加非研究必需模块。

Phase 1 已完成不表示停止维护；影响后续阶段正确性的缺陷仍应优先修复。

## 8. Phase 2A：最小动态 FJSP 底座

**状态：`Active`**

### 作用

在不引入运输、AGV 或学习框架的前提下，建立动态事件和确定性重调度的最小闭环。

### 当前范围

- 机器故障与维修事件。
- 新 Job 到达事件。
- 未来工序加工时间变化事件。
- 动态状态与有序事件时间线。
- 已完成和正在执行记录的冻结快照。
- 剩余工序视图。
- FIFO、SPT 和 EFT 最小重调度基线。
- 静态与动态双重 feasibility check。
- JSON 事件文件审计、回放和动态总览报告。

### 当前明确不做

- AGV、运输时间、路径和碰撞。
- RL、DQN、PPO、GNN 和多智能体。
- 能耗、多目标 Pareto 优化和完整论文算法复现。
- 随机仿真器和大规模工业数字孪生。

### 退出条件

Phase 2A 只有在以下条件全部满足后才能申请进入 Phase 2B：

1. 所有动态事件具有明确的数据契约、边界检查和单元测试。
2. 冻结工序不可被重调度修改，且相关违规能够返回明确诊断。
3. 所有重调度结果同时通过静态和动态 feasibility checker。
4. 非法 ID、重复事件、同时间事件和冻结工序加工时间变化具有明确处理规则。
5. 动态 smoke、事件文件审计和事件回放可以在 CI 中稳定复现。
6. 总体测试通过，核心覆盖率不低于 80%。
7. `AGENTS.md`、README、数学模型和审查状态相互一致。
8. 完成最小公开库兼容性试验，记录采用适配器、仅作基线或不采用的理由。
9. 选定至少一个公开、可复现的非学习型动态基线；完整论文算法复现仍需单独批准。

## 9. Phase 2B：事件驱动动态仿真与评价

**状态：`Planned`**

### 进入条件

- Phase 2A 退出评审通过。
- 动态事件语义和重调度接口稳定。
- 至少完成一次动态 FJSP 近邻文献审查和强基线选择。
- 已明确哪些仿真、Dispatcher 和可视化能力复用公开库，哪些属于项目特有语义。

### 作用

将单次事件回放升级为可以连续推进时间、重复触发事件并系统评价重调度策略的动态实验环境。

### 候选交付物

- 事件驱动仿真循环和确定性时间推进。
- 多次故障、维修、新订单和加工时间变化的连续场景。
- 周期触发与事件触发重调度策略。
- makespan、延误、运行时间和调度稳定性指标。
- 可配置场景生成器、固定随机种子和动态 benchmark 协议。
- 完全重调度、局部修复和自适应规则选择基线。

### 验证标准

- 相同输入和随机种子产生可复现事件轨迹与调度结果。
- 每次状态转换和每次重调度都有合法性记录。
- 能够区分算法失败、场景无解、超时和非法调度。
- 评价指标定义、计算方式和实验预算写入实验元数据。

### 退出条件

- 动态仿真闭环能够在多实例、多扰动强度下稳定运行。
- 至少一个非学习型动态方法完成强基线对比、消融和统计实验。
- 是否进入 AGV 阶段经过独立评审，而不是由项目名称自动决定。

## 10. Phase 3：运输资源与 AGV 协同调度

**状态：`Planned`**

### 进入条件

- Phase 2B 退出评审通过，或者经过评审决定从稳定静态平台直接建立独立 AGV 分支。
- 完成 FJSP-transport、FJSP-AGV 和联合调度近邻文献矩阵。
- 明确运输假设、AGV 类型、目标函数和 benchmark 来源。
- 评估 OR-Tools、PyJobShop、JobShopLib 及论文开源实现能够复用的约束、求解和可视化能力。
- 形成“直接使用、适配、扩展或自研”的逐项决策记录。

### 作用

把运输从隐含零时间过程提升为显式资源，使机器加工和物料运输能够联合建模、联合校验和联合优化。

### Phase 3A 候选范围：运输资源基础

- 机器位置和运输时间矩阵。
- 工序之间的显式运输任务。
- 有限、同质、单位容量 AGV。
- 空载与载货移动时间。
- 机器、工序和 AGV 联合调度结果。
- 运输层 feasibility checker。
- 小规模 CP-SAT 或 MILP 参考模型与启发式基线。

通用区间变量、资源不重叠和精确求解优先交给 OR-Tools；项目重点维护运输语义、
AGV 状态、联合结果和联合 checker，不自行实现通用约束求解器。

### Phase 3B 候选范围：路径与冲突

只有 Phase 3A 验证后，才评审以下内容：

- 异质 AGV、容量差异和电量约束。
- 路网、节点占用、边冲突和避碰。
- 缓冲区、阻塞、充电和维护资源。
- 动态 AGV 故障与运输任务重分配。

### 验证标准

- 加工合法性和运输合法性分别检查，并提供联合结果。
- 小实例能够与精确模型或人工可验证结果对照。
- 顺序求解与联合求解使用相同数据和预算进行比较。
- 路径冲突未被显式建模前，不得声称已经解决 AGV 避碰问题。

### 退出条件

- 至少一个完整 FJSP-AGV 调度闭环通过联合 feasibility checker。
- Benchmark、基线、实验协议和失败语义稳定。
- 是否进入 RL 阶段由传统方法瓶颈和研究问题共同决定。

## 11. Phase 4：强化学习环境与可信基线

**状态：`Planned`**

### 进入条件

- 被学习的静态、动态或 AGV 环境已经具有稳定的非学习接口。
- 存在可复现的启发式、元启发式或精确方法基线。
- 明确 RL 要解决的具体决策，而不是仅以“使用 RL”作为目标。
- 完成 JobShopLib、Gymnasium 和最近邻开源 RL 环境的复用评估。
- 若决定自研环境，必须记录公开环境无法满足的具体语义或验证要求。

### 作用

把已验证的调度环境封装为可训练、可评估、可复现的序贯决策环境，并建立最小学习基线。

### 候选交付物

- 明确的 MDP：状态、动作、转移、奖励和终止条件。
- 合法动作掩码和无效动作处理规则。
- 训练、验证和测试实例严格分离。
- 固定随机种子、模型检查点和实验配置。
- 一个简单、可复现的 RL 基线。
- 与启发式、随机策略和强传统方法的公平比较。

观察空间包装、训练循环、图数据结构和通用可视化优先复用成熟实现；项目自研范围集中在
调度环境语义、合法动作、状态转换、奖励定义、结果转换和 feasibility gate。

### 验证标准

- 环境在不训练的情况下通过状态转移和合法性测试。
- RL 策略产生的每个最终调度都通过对应 feasibility checker。
- 报告多次独立训练结果，而不是只展示最好一次。
- 报告训练成本、推理时间、泛化结果和失败案例。
- 只与弱规则比较不能支持“优于现有方法”的结论。

### 退出条件

- 学习环境、训练流程和评估流程可独立复现。
- RL 基线在预先定义的指标上具有稳定、可解释的结果。
- 是否引入 GNN 或多智能体由普通表示和单智能体方法的实际限制决定。

## 12. Phase 5：GNN、多智能体与高级学习方法

**状态：`Hold`**

### 启用条件

以下条件未满足时，本阶段保持 `Hold`：

1. Phase 4 已验证普通状态表示或单智能体方法存在明确瓶颈。
2. 文献审查证明拟议方法不是已有工作的直接重复。
3. 至少一个公开强基线已经成功复现。
4. 已定义能够验证新结构贡献的消融实验。
5. 已评估 JobShopLib、PyTorch Geometric 和最近邻论文开源图环境，确认不能直接满足研究问题。

### 候选研究方向

- 可变规模工序—机器—AGV 异构图表示。
- 分层决策和联合动作分解。
- 多智能体协同、集中训练与分散执行。
- 跨规模、跨扰动和跨车间实例泛化。
- 精确方法、启发式与学习方法的混合求解。

### 验证标准

- GNN 或多智能体必须解决已经观察到的问题，而不是为了增加模型复杂度。
- 必须与去除图结构、去除协同机制等消融版本比较。
- 参数量、训练预算和推理预算必须公开并保持比较公平。
- 不得用工程工作量代替学术贡献证明。

## 13. Phase 6：长期平台成果

**状态：`Planned`**

长期平台成熟后，应形成以下可独立使用和审查的成果：

- 统一的静态、动态和运输资源问题数据协议。
- 可插拔的启发式、精确方法、元启发式和学习算法接口。
- 可选公开库适配器及其语义兼容性报告。
- 分层 feasibility checker 与违规诊断系统。
- 标准 benchmark、动态场景和 AGV 场景元数据。
- 可复现实验运行器、CSV/JSON 结果、图表和报告。
- 算法质量、稳定性、运行时间、泛化和失败案例分析。
- 面向论文、教学或后续研究的版本化平台发布物。

最终成果的意义不是堆叠所有算法，而是建立一个统一坐标系，使不同方法能够在
相同问题定义、相同合法性约束和相同实验预算下被公平比较。

## 14. 阶段评审规则

申请切换活动阶段时，必须完成以下检查：

1. 当前阶段的交付物和退出条件逐项验证。
2. 所有测试和相关实验命令实际运行成功。
3. 工作树状态、依赖版本和实验产物被记录。
4. 新阶段具有明确研究问题、输入输出和非目标。
5. 完成必要的近邻文献矩阵和强基线选择。
6. 新增约束已经设计独立 feasibility checker。
7. 对通用能力完成公开库调查，并记录复用、适配或自研理由。
8. 更新仓库内 `AGENTS.md`、README、本文件和审查状态。
9. 未通过评审时，下一阶段保持 `Planned` 或 `Hold`。

## 15. 与硕士论文的关系

本路线描述长期平台，而不是承诺硕士论文必须实现全部阶段。

硕士论文应从平台路线中选择一个边界清晰的问题，并满足：

- 问题定义和假设明确。
- 与最近邻文献的差异有证据支持。
- 至少一个可识别的本文方法或实践贡献。
- 使用足够强且公平的基线。
- 所有结果通过合法性检查。
- 具有消融、敏感性、统计或泛化实验。
- 结论由结构化实验产物支持。

AGV、动态事件、RL、GNN 和多智能体本身均不是创新点。论文是否采用其中任何一项，
由文献差距、研究问题、时间预算和阶段验证结果决定。
